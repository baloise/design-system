# Plan: Prefix component CSS classes with `ds-`

## Context

The design system's CSS-only consumption mode (no Shadow DOM, no custom elements — see "Hybrid Component Model" in `docs/ARCHITECTURE.md`) ships bare, generic class names like `.button`, `.card`, `.badge`. At least one consuming CMS uses the same generic class names for its own markup. When the design system's CSS is loaded alongside the CMS's CSS, these names collide — the CMS's `.button` styles and the design system's `.button` styles fight over the same selector, with unpredictable results depending on load order and specificity.

Prefixing every component root and structural sub-element class with `ds-` (`.button` → `.ds-button`, `.badge` → `.ds-badge`) namespaces the whole design system's CSS-only surface so it can never collide with a CMS's (or any other consumer's) own class names, without touching the CMS itself.

Two related conventions are explicitly **not** part of this change:
- **Modifier classes** (`is-*`, `has-*`, e.g. `.is-primary`, `.has-shadow`) stay as-is — they're always used in combination with a (now-prefixed) base class, so they don't carry collision risk on their own.
- **Utility classes** (`bg-primary`, spacing/typography/etc., generated by the UnoCSS preset in `packages/css/src/preset/rules/**`) stay as-is — out of scope by explicit decision.

CSS custom properties (`--button-color-text`, etc.) are also explicitly out of scope — this migration only touches class selectors.

There's an existing half-finished precedent for this exact pattern in `packages/core/src/components/form/form.style.scss`, where `.field` and `.ds-field` currently exist as synonyms. This migration supersedes that by completing the rename everywhere, in one atomic pass, rather than leaving a mixed state.

## Decisions made

- **Hard cutover, no transition period.** All components are renamed in a single coordinated migration; old class names are removed, not kept alongside new ones. A dual-class transition would undermine the collision-avoidance goal and extend the inconsistent `.field`/`.ds-field` state this change is meant to fix.
- **All ~48 components, one PR.** Not phased/gradual — avoids a long-lived mixed state.
- **Sub-element/structural classes are prefixed too** (`.badge`, `.icon-left`, `.icon-right`, `.buttons`, `.table-container`, `.stack-content`, `.col`, `.field`, etc.) — same collision risk as root classes, since they're equally generic, bare nouns.
- **Modifiers, utilities, and CSS custom properties are out of scope.**
- **Shipped as a breaking change** via changeset (major bump for `@baloise/ds-core`), since existing CSS-only consumers must update their markup.
- **Migration is scripted**, not hand-edited, given the number of files and the need for consistency across source, stories, and test fixtures.
- **Record an ADR** (`docs/adr/0022-ds-prefix-component-classes.md`) — this is the kind of decision that's hard to reverse (breaking change, wide blast radius), non-obvious from the code alone (a reader would wonder why `.button` suddenly became `.ds-button`), and the result of a real trade-off (hard cutover vs. dual-class transition, scoped-in sub-elements vs. root-only). Content:

  ```md
  # Prefix component CSS classes with `ds-`

  The design system's CSS-only consumption mode ships bare component class
  names (`.button`, `.card`, `.badge`, ...). At least one consumer embeds
  this CSS alongside a CMS that uses the same generic class names, causing
  style collisions. We're prefixing every component root and structural
  sub-element class with `ds-` (`.button` → `.ds-button`) to namespace the
  design system's class surface and eliminate this collision risk.

  Modifier classes (`is-*`, `has-*`) and utility classes (`bg-*`, generated
  by the `packages/css` UnoCSS preset) are unaffected — modifiers are only
  ever used alongside a (now-prefixed) base class, and utilities are a
  separate, already-namespaced-by-function system. CSS custom properties
  are also unaffected.

  This is a hard cutover, not a dual-class transition: old class names are
  removed outright, shipped as a breaking change. A transition period
  (keeping both `.button` and `.ds-button` working, as `form.style.scss`
  already does for `.field`/`.ds-field`) would leave the collision risk
  live during the transition and extend the inconsistent mixed state this
  change is meant to resolve.
  ```

## Implementation

### 1. Build the rename map

Enumerate every component base/sub-element class before writing the script — don't infer it programmatically. Source: every `*.style.scss` under `packages/core/src/components/**`, both the `$css-selector` SCSS-variable pattern (e.g. `packages/core/src/components/button/button.style.scss:10`) and literal selectors (e.g. `packages/core/src/components/container/container.style.scss:12`). Exclude:
- Modifier selectors (`is-*`, `has-*`)
- Anything already prefixed (`.ds-app`, `.ds-field`, `.ds-footer-link-list`) — just drop the now-redundant unprefixed synonym (e.g. `.field` in `form.style.scss`)
- Descendant selectors that target **custom element tag names**, not classes — e.g. `table.style.scss:220,231` reference `ds-checkbox`/`ds-button` as element selectors (`ds-button { ... }`), not classes (`.ds-button`). These are a visual homonym after the rename but not an actual collision (tag selectors vs. class selectors are distinct in CSS). Flag them in the PR description as a review-caution; no code change needed there beyond what the script naturally leaves alone (it should only ever match `.foo`, never bare `foo`).

### 2. Write a one-time migration script

`scripts/rename-component-classes.mjs` (not kept long-term), driven by the curated map from step 1:

1. Rewrite `$css-selector` values and literal `.foo { }` selectors in `packages/core/src/components/**/*.style.scss` — this is the single source of truth for both Shadow DOM host mode and CSS-only mode (see `docs/ARCHITECTURE.md` "Hybrid Component Model"), so fixing it here fixes both consumption modes.
2. Rewrite hardcoded HTML in Storybook stories, `apps/storybook/src/components/**/*.stories.ts` (e.g. `card.stories.ts:56-57`, `radio.stories.ts:238-239`) that write `class="button is-secondary"` directly.
3. Rewrite the dedicated CSS-only visual-regression fixtures, `packages/core/src/components/**/test/*.style.html`.
4. Leave Playwright visual snapshot regeneration as a manual follow-up (screenshots require rendering, not text replacement) — use the `ds-update-screenshots` skill/bot command against affected components after the PR is up.

Model the script's structure (pure logic module + thin CLI wrapper) on `scripts/token-usage/lib/scan.mjs` + `scripts/generate-token-usage.mjs`, the closest existing precedent for a scan/transform script in this repo.

### 3. Rebuild derived artifacts

- Rebuild the compiled CSS bundle consumed by Storybook test fixtures (`apps/storybook/public/assets/css/design-system.css` / `design-system.local.min.css`) via `pnpm css`.
- Update prose/examples in `docs/STYLE_GUIDE.md`, `docs/ARCHITECTURE.md`, and `packages/core/CONTEXT.md` wherever they show `.button`/`.card`-style examples, so documentation doesn't teach the old convention.

### 4. Changeset

Add a changeset for `@baloise/ds-core` (major bump), following the format in `.changeset/*.md` (frontmatter package + bump, then description), explicitly calling out the breaking rename and pointing to ADR-0022 for rationale.

### 5. ADR

Create `docs/adr/0022-ds-prefix-component-classes.md` with the content drafted above.

## Verification

- `pnpm build` and `pnpm tokens`/`pnpm css` succeed with no leftover references to old class names (`grep -rn "class=\"button\|class=\"card` etc. across `apps/storybook` and `packages/core` should return nothing except intentionally-preserved modifier-only usages).
- `pnpm test` (Vitest) passes.
- `pnpm play` visual/component Playwright suites: expect the renamed-class fixtures to fail on first run (old baselines won't match new markup) — regenerate baselines via the `ds-update-screenshots` skill for every affected component, then re-run to confirm green.
- Manually open Storybook (`pnpm docs`) for `button` and `card` and confirm both Shadow DOM (`<ds-button>`) and CSS-only (`<button class="ds-button ...">`) render identically to before, just under the new class name.
