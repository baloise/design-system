# CONTEXT — packages/angular (Angular Bindings)

This document captures domain language, architectural patterns, and key concepts specific to the Angular bindings package.

## Overview

**packages/angular** (`@baloise/ds-angular`) is a thin, published wrapper around the Stencil-generated web components in `packages/core`, giving Angular consumers standalone Angular component wrappers (inputs, typed outputs, methods) instead of raw custom elements.

It is generated, not hand-authored: the Angular wrappers themselves come from `@stencil/angular-output-target`, invoked directly from `packages/core/config/stencil.bindings.angular.ts` as part of the core build (see [[packages/core|packages/core/CONTEXT.md]]). This package needs no custom output-target logic — see [ADR-0006](../../docs/adr/0006-ds-angular-uses-stock-output-target.md), which retired the previous hand-rolled `libs/output-target-angular` generator in favor of the stock package.

## Core Concepts

### Generated vs. authored code

- `src/generated/proxies.ts`, `src/generated/proxies-list.ts`, `src/generated/angular-component-lib/utils.ts` — fully generated by the Stencil Angular output target on every `@baloise/ds-core` build. Never hand-edited; regenerate from scratch each build.
- `src/index.ts` — re-exports the generated components and exposes `bootstrapDesignSystem()`, a thin call into `@baloise/ds-core`'s `initializeDesignSystem()` for Angular apps that want to set brand/region/language defaults.
- `src/forms/` — hand-authored `ControlValueAccessor` support for reactive-forms (see "Reactive-forms integration" below). Same category as `src/index.ts`: not retired by regenerating from Stencil.
- `src/providers/` (planned) — hand-authored, non-generated services that need real Angular DI (e.g. a modal service using a scoped ref/injection-token pattern; see [ADR-0022](../../docs/adr/0022-modal-overlay-component-delegate-pattern.md)). Unlike the generated component wrappers, these aren't retired by regenerating from Stencil — they're this package's own code, same category as `src/index.ts`.

### Standalone, not NgModule-based

Generated with `outputType: 'standalone'` — every `ds-*` component is a standalone Angular component/directive with no accompanying `NgModule`. Consumers import components directly. This is deliberate: the package only supports the newest Angular major version, where standalone is the default component style.

### Self-registering custom elements

Configured with `customElementsDir: 'components'`, matching `packages/react`'s pattern: each generated component imports and calls `defineCustomElement` for its own tag on load. Consumers don't need a separate `defineCustomElements()`/bootstrap call before using a `ds-*` component in a template — only `bootstrapDesignSystem()` if they want non-default config (brand/region/language).

### Build

Built with `ng-packagr` (`ng-packagr -p ng-package.json -c tsconfig.lib.json`), producing Angular Package Format output — unlike `packages/react`/`packages/tokens`'s plain `tsc` compile. This matches Angular library publishing convention and how the old pre-shadow-DOM `packages/angular` was built; a plain `tsc` compile risks AOT/Ivy compilation issues for downstream consumers.

`ng-packagr@22` requires TypeScript `>=6.0 <6.1`, one major ahead of the rest of the monorepo's `typescript: 5.6.3` catalog entry. This package pins its own `typescript`/`ng-packagr`/`@angular/*` devDependency versions instead of using `catalog:`, which pnpm's non-hoisted `node_modules` layout supports without affecting other packages.

### Reactive-forms integration

Consumers must never have to opt in to reactive-forms support by importing anything beyond the component they already use to render the element — no extra directive in a standalone component's `imports` array. This is why `ControlValueAccessor` (CVA) is wired onto the exact wrapper class consumers import (e.g. `DsInput`), not onto a separate directive matched by CSS selector: a standalone Angular directive only applies within a template whose component explicitly lists it in `imports`, so a separate `@Directive({selector: 'ds-input'})` would force every consumer to import it by hand alongside `DsInput` — the opposite of "just works".

`src/forms/value-accessor.ts` exports `DsValueAccessor<Value>`, a plain (undecorated) class implementing `ControlValueAccessor` via **composition**, not inheritance: the concrete wrapper (e.g. `DsInput`) already extends the generated proxy class for its inputs/outputs, and Angular doesn't allow a `@Directive()` to extend a `@Component()` (`NG0903: Directives cannot inherit Components` at runtime) — so the CVA logic can't live in a base/mixin class the wrapper also `extends`. Instead the wrapper constructs one as a field (`new DsValueAccessor(inject(ElementRef).nativeElement, inject(Injector), config)`) and delegates its four `ControlValueAccessor` methods, plus `init()`/`destroy()` from its own `ngOnInit`/`ngOnDestroy`, to it. `DsValueAccessor` deliberately implements no Angular-recognized lifecycle interface and isn't `@Injectable()` — it's always constructed and driven manually, never resolved by Angular's own DI, so `element`/`injector` are passed in explicitly rather than it calling `inject()` itself (either would make `ng-packagr`'s AOT compiler expect an Angular-native factory/lifecycle, which a manually-constructed helper can't satisfy). `config` declares `changeEvent` (the DOM event carrying value changes, e.g. `dsChange`) and `valueProp` (the property to write, e.g. `value`); it handles `writeValue`/`registerOnChange`/`registerOnTouched`/`setDisabledState`, plus deriving `invalid`/`invalidText` from the host's `NgControl` once the control is touched and invalid (skipped entirely when the component's `autoInvalidOff` prop is `true`).

`src/forms/ds-input.ts` exports the first concrete usage: `class DsInput extends DsInputElement implements ControlValueAccessor`, re-declared with its own `@Component({selector: 'ds-input', ...})` and the `NG_VALUE_ACCESSOR` provider — `DsInputElement` being the generated proxy from `src/generated/proxies.ts`, imported under an alias. `src/index.ts` re-exports this hand-authored `DsInput` (an explicit named export always wins over the ambiguous `export * from './generated/proxies'` for the same name, per ES module semantics) so consumers keep importing exactly one `DsInput` — the generated one is never visible. Plain prototype members (the native element reference, the generated `setFocus`/`getInputElement`-style methods) inherit from the base class for free via normal JS inheritance — but `inputs`/`outputs` do **not**: Angular's compiler resolves a component's inputs/outputs statically from its own `@Component` decorator at build time, so the subclass's decorator re-lists them verbatim (a `NG8002: Can't bind to '…'` template error otherwise). Keep that list in sync with the generated `DsInput`'s `@Component` decorator whenever `ds-input`'s props/events change — there's no way around this duplication without post-processing the generated output. This is the tracer-bullet pattern every other form-component ticket (`ds-input-stepper`, `ds-textarea`, `ds-date`, `ds-number-input`, `ds-radio-group`, `ds-select`, …) is expected to reuse via its own `src/forms/ds-<component>.ts`.

Resolving `NgControl` happens in `DsValueAccessor.init()` (called from `DsInput.ngOnInit()`) via `Injector.get()` rather than constructor injection, to avoid a circular dependency (`NgControl` depends on the `NG_VALUE_ACCESSOR` this component provides). Subscribing to the resolved control's `events` is further deferred to a microtask, because `NgControl.control` (e.g. `FormControlName.control`) is itself assigned by that directive's own `ngOnChanges` — which has no guaranteed order relative to this component's own `ngOnInit`. `events` (not `statusChanges`) is used so a bare `markAsTouched()`/`markAllAsTouched()` (e.g. a submit-button pattern with no value or status change) still re-derives invalid state.

This retires the "no form component / reactive-forms integration" limitation from [ADR-0006](../../docs/adr/0006-ds-angular-uses-stock-output-target.md) for `ds-input`, following the "thin wrapper layer on top of the generated standalone components" path that ADR anticipated; other form components still get only the plain generated wrapper until their own ticket adds a `withValueAccessor` usage.

### Verifying the package works

The package's real-world behavior (does it actually work when installed by an Angular app?) is verified separately by the integration app in `apps/integration-angular/`, not by unit tests in this package. See `docs/adr/0009-integration-apps-as-workspace-members.md` for why that app is a normal workspace member resolving this package via `workspace:*`.

Watch for `NG0203` (duplicate `@angular/core` instances) if this package's build ever changes to expose its own devDependency-installed `node_modules` to consumers — pnpm's workspace protocol only exposes what `dependencies` declares (`@baloise/ds-core`, `tslib`), not this package's own `@angular/core` devDependency (needed only for its `ng-packagr` build), so the consuming app's bundler sees a single `@angular/core` instance.

**Also required:** `ng-packagr` must build in Ivy **partial** compilation mode (`angularCompilerOptions.compilationMode: "partial"` in `tsconfig.json`), not the default full mode — full compilation pre-bakes directive factories against `ng-packagr`'s own compiler instance instead of letting the consuming app's Angular compiler link them, which also produces `NG0203`.

## Key Constraints

- `@angular/core` / `@angular/common` are `peerDependencies` (`>=22.0.0`) — consumers supply their own version. Only the newest Angular major is supported.
- `rxjs` (`>=7.8.0`) is also a `peerDependency` — required at build time by the generated `angular-component-lib/utils.ts` helper file, even though this MVP's components don't expose Observable-based outputs.
- **Reactive-forms integration is opt-in per component to build, but zero-config for consumers once added.** Only `ds-input` currently has a `ControlValueAccessor` (see "Reactive-forms integration" above); consumers get it automatically just by using `DsInput`, no extra import. Every other form component (`ds-select`, `ds-checkbox`, `ds-date`, …) still gets the same plain wrapper as any other component — inputs, outputs, methods — with no `NG_VALUE_ACCESSOR` wiring, until its own ticket adds one.
- No SSR/hydrate support yet — client-side only.
- No component exclusions — every `ds-*` component gets an Angular wrapper.
