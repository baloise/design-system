## What are Design Tokens?

Design tokens are **named, reusable design decisions** stored as data rather than hard-coded values. Instead of writing `background-color: #005EFF` in your CSS, you write `background-color: var(--ds-button-primary-color-bg-base)`.

This approach provides:
- **Single source of truth** — designers and developers reference the same values
- **Easy rebranding** — change one token, update everywhere automatically
- **Consistency** — all components automatically stay aligned

---

## The Four-Layer Architecture

Tokens are organized into four layers, each building on the one below:

<TokenLayersDiagram />

### 🌐 **Global Tokens** — Raw Values

The foundation: every concrete value your system uses.

**Never used directly in components.** They exist as building blocks for layers above.

### 🔗 **Alias Tokens** — Meaning & Intent

Assign purpose to raw values. This is where design decisions live.

**Used by designers** when creating themes. Changing an alias token cascades to all components that reference it.

### 📱 **Device Tokens** — Responsive Values

Alias values that change per breakpoint (typography sizes, spacing) — the bare token
auto-switches between mobile, tablet, and desktop as the viewport changes.

**Used by developers** for any value that should respond to screen size.

### 🧩 **Component Tokens** — UI-Specific Values

Map alias and device tokens to specific component states and variants.

**Used by developers** when building components.

## Token Naming Pattern

<img src={tokenNamingAnatomy} alt="Token name anatomy segments" style={{ width: '100%', margin: '2rem 0' }} />

Token names are composed of ordered segments that narrow scope:

```
--ds  -  component  -  variant  -  element  -  category  -  property  -  state
```

### Example: Button Primary Color

```
--ds-button-primary-color-bg-base
  │    │       │       │     │  │
  │    │       │       │     │  └─ state (base, hover, active, disabled)
  │    │       │       │     └─ property (bg = background, text = color, border)
  │    │       │       └─ category (color, font, space)
  │    │       └─ variant (primary, secondary, ghost)
  │    └─ component (button, input, tag)
  └─ namespace
```

### Naming Rules

**Typography tokens** use `font-` prefix:
- `--ds-button-font-size` ✅ (not `--ds-button-size`)
- `--ds-button-font-weight` ✅ (not `--ds-button-weight`)

**Color order** — variant comes before category:
- `--ds-button-primary-color-text` ✅
- ❌ `--ds-button-color-primary-text` (wrong order)

**State is required** for colors:
- `--ds-button-primary-color-bg-base` ✅
- ❌ `--ds-button-primary-color-bg` (missing state)

## How Device Tokens Auto-Switch

**Always prefer the bare `--ds-device-*` name** in component code — it auto-switches at
breakpoints. The `-mobile`/`-tablet`/`-desktop` variants exist only for special cases where you
need to force a specific breakpoint's value.

```css
:root {
  --ds-device-text-size-xl: var(--ds-font-size-28);  /* mobile: 1.75rem */
}

@media (min-width: 769px) {
  :root {
    --ds-device-text-size-xl: var(--ds-font-size-40); /* tablet: 2.5rem */
  }
}

@media (min-width: 1024px) {
  :root {
    --ds-device-text-size-xl: var(--ds-font-size-40); /* desktop: 2.5rem */
  }
}
```

## Using Tokens

In your own CSS, reference tokens directly as CSS variables:

```css
.my-card {
  background: var(--ds-bg-color-primary);
  padding: var(--ds-space-16);
  border-radius: var(--ds-radius-base);
}
```

For more examples, see [Use Tokens in Code](?path=/docs/tokens-use-tokens-in-code--documentation).

Every component also exposes its own tokens as public CSS variables, so you can override
individual instances without touching the component's internals — see
[Component Variables](?path=/docs/tokens-component-variables--documentation).
