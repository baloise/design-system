## Installation

If you do not have an Angular app yet, create one with [Angular CLI](https://angular.io/guide/setup-local).

<InfoQuote>
  **Recommendations**

  - Use **SCSS** as stylesheet format to access breakpoint mixins and more. A pre-built CSS bundle is also available.
  - Angular **17+** with standalone components is required — the Design System ships no `NgModule`.
</InfoQuote>

Install the Angular bindings and the global styles. All three packages are required.

```bash
npm add -E @baloise/ds-angular @baloise/ds-styles @baloise/ds-tokens
// or
pnpm add -E @baloise/ds-angular @baloise/ds-styles @baloise/ds-tokens
```

## Usage

### Import Styles

Add these to your global stylesheet (e.g. `styles.scss`). Only **Tokens** and
**Foundation + Components** are required — add Utilities as you need it:

```css
/*
  Required: design tokens (--ds-* CSS custom properties).
  Load before ds-styles
*/
@import '@baloise/ds-tokens/css/base';

/*
  Required: CSS reset, structural styles, and
  CSS-only component classes (e.g. class="ds-button")
*/
@import '@baloise/ds-styles/css/design-system';

/*
  Optional: only needed if you use utility classes
  (spacing, layout, typography, color helpers, etc. — e.g. class="mt-base" below)
*/
@import '@baloise/ds-styles/css/utilities';
```

For SASS mixins (breakpoints, etc.) without any styles, import `@baloise/ds-styles/scss/mixins` instead.

### provideDesignSystem

Angular apps are standalone by default. Add `provideDesignSystem()` to the providers in `app.config.ts` — it
initializes the system once and every nested component picks up brand, region, language, and animation settings.

```typescript
// app.config.ts

import { ApplicationConfig } from '@angular/core'
import { provideDesignSystem } from '@baloise/ds-angular'

export const appConfig: ApplicationConfig = {
  providers: [
    provideDesignSystem({
      defaults: {
        region: 'CH',
        language: 'de',
        allowedLanguages: ['de', 'fr', 'it', 'en'],
      },
    }),
  ],
}
```

Pass the default config via `defaults`. If you omit it, components still work with the default config. Region and
language can also be changed at runtime with `updateDsRegion` / `updateDsLanguage`. See **Development/Configuration**.

```typescript
// main.ts

import { bootstrapApplication } from '@angular/platform-browser'

import { App } from './app/app'
import { appConfig } from './app/app.config'

bootstrapApplication(App, appConfig).catch(err => console.error(err))
```

Every component — including layout elements like `DsRoot` and `DsAppFooter` — ships as a real, standalone Angular
component generated from the underlying web component. Import what you need directly; no `CUSTOM_ELEMENTS_SCHEMA` is
required.

```typescript
// app.ts

import { Component } from '@angular/core'
import { DsAppFooter, DsButton, DsRoot } from '@baloise/ds-angular'

@Component({
  selector: 'app-root',
  imports: [DsRoot, DsAppFooter, DsButton],
  templateUrl: './app.html',
})
export class App {}
```

Add `ds-root` to your root template. Elements like the heading below are plain HTML styled with a CSS class — no
import or registration needed.

```html
<!-- app.html -->

<ds-root class="has-sticky-footer">
  <header>
    <!-- Header content -->
  </header>
  <main class="ds-container">
    <!-- Your application content -->
    <h1 class="ds-heading">Hello World!</h1>
    <ds-button>Button</ds-button>
  </main>
  <ds-app-footer>
    <!-- Footer content -->
  </ds-app-footer>
</ds-root>
```

## Default HTML

Just an `index.html` file. This is the recommended setup for static sites, server-rendered
pages, or any HTML5 app you keep under version control with npm.

```bash
npm add -E @baloise/ds-core @baloise/ds-styles @baloise/ds-tokens
// or
pnpm add -E @baloise/ds-core @baloise/ds-styles @baloise/ds-tokens
```

### Usage

Create an `index.html` file in your project root and add the following:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Helvetia Design System</title>

    <!-- Configure the Design System before it boots -->
    <meta
      name="design-system-config"
      data-brand="helvetia"
      data-region="CH"
      data-language="de"
      data-allowed-languages="de,fr,it,en"
    />

    <!-- Required: design tokens (--ds-* CSS custom properties). Load before ds-styles -->
    <link rel="stylesheet" href="node_modules/@baloise/ds-tokens/css/base" />
    <!-- Required: CSS reset, structural styles, and CSS-only component classes (e.g. class="ds-button") -->
    <link rel="stylesheet" href="node_modules/@baloise/ds-styles/css/design-system" />
    <!-- Optional: only needed if you use utility classes (spacing, layout, typography, color helpers, etc. — e.g. class="mt-base" below) -->
    <link rel="stylesheet" href="node_modules/@baloise/ds-styles/css/utilities" />

    <!-- Register the web components used in markup -->
    <script
      type="module"
      src="node_modules/@baloise/ds-core/dist/design-system/design-system.esm.js"
    ></script>
    <script nomodule src="node_modules/@baloise/ds-core/dist/design-system/design-system.js"></script>

  </head>

  <body>
    <ds-root>
      <main class="ds-container mt-base">
        <h1 class="ds-heading">Hello World</h1>
        <button class="ds-button">Button</button>
      </main>
    </ds-root>
  </body>
</html>
```

Here's a complete, working page — the language/region `<meta>` tag, stylesheet, and scripts all
live in `<head>`; `ds-root` wraps the page content in `<body>`.

<br />

**What each part does**

- **`<meta name="design-system-config">`** — sets brand, region, and language before the app
  boots. Optional, but recommended so there's no flash of default config. See "Configure Language
  & Region" further below.
- **The three stylesheets** — `base.tokens.css` (from `@baloise/ds-tokens`) defines every `--ds-*`
  custom property and must load first — `ds-styles` no longer ships token values itself, only
  `var(--ds-*)` references. `design-system.css` (from `@baloise/ds-styles`) bundles the CSS reset,
  structural styles, and CSS-only component classes (`.ds-button`, `.ds-heading`, ...) — the only
  one you really need alongside tokens. `utilities.css` (spacing, layout, typography, color
  helpers, e.g. `.mt-base` used below) is entirely optional — drop it if you don't use utility
  classes. See **Development/Theming** for the ERV brand token files.
- **`<script type="module">` / `<script nomodule>`** — registers the web components (`<ds-root>`,
  `<ds-stage>`, etc.) used in markup. The `nomodule` variant is a fallback for browsers without
  ES module support.
- **`<ds-root>`** — the root layout web component; wrap your page content in it.
- **`<h1 class="ds-heading">` / `<button class="ds-button">`** — plain HTML styled with a CSS
  class. No script needed for these — only elements that need JS behavior (like `<ds-root>`) are
  web components.

## Server-Side Rendering (SSR)

For a CMS or any server-rendered page, components can be pre-rendered to real HTML before they
reach the browser — useful for SEO, faster first paint, and CMS previews that don't execute
JavaScript. `@baloise/ds-core` ships a Node-compatible renderer for this that has no framework
dependency. The example below uses [Express](https://expressjs.com/), but `renderToString` itself
works with any Node server.

Install the same three packages as the "Default HTML" setup above — `ds-styles` and `ds-tokens`
are still required for the browser to render the page correctly; only the renderer itself
(`renderToString`) is additive on top of `ds-core`. Add `express` to serve the page and its
assets, and `copyfiles` as a dev dependency to stage those assets at build time.

```bash
npm add -E @baloise/ds-core @baloise/ds-styles @baloise/ds-tokens express
npm add -D -E copyfiles
// or
pnpm add -E @baloise/ds-core @baloise/ds-styles @baloise/ds-tokens express
pnpm add -D -E copyfiles
```

### Stage the client assets

The browser still needs the design-system loader script and the tokens/styles CSS — none of
which live in a ready-to-serve folder inside `node_modules`. Add a `copy-assets` script that
stages them into a `public` folder next to the server, and run it before `dev`/`start`/`build`
via the matching `pre*` lifecycle scripts:

```json
{
  "scripts": {
    "copy-assets": "copyfiles -u 5 \"node_modules/@baloise/ds-core/dist/design-system/**/*\" public/design-system && copyfiles -f node_modules/@baloise/ds-tokens/dist/css/base.tokens.css node_modules/@baloise/ds-styles/dist/css/design-system.css public",
    "predev": "pnpm copy-assets",
    "dev": "tsx watch server.ts",
    "prestart": "pnpm copy-assets",
    "start": "tsx server.ts",
    "prebuild": "pnpm copy-assets",
    "build": "tsc --noEmit"
  }
}
```

The first `copyfiles` call copies the design-system JS entry and all of its lazily-loaded
component chunks (Stencil splits every component into its own file) into `public/design-system`,
preserving that folder structure. The second copies the two CSS bundles straight into `public`.
`-u 5` strips the five leading path segments (`node_modules/@baloise/ds-core/dist/design-system`)
so only the files themselves land in the destination; `-f` flattens the CSS sources to their
basenames.

### Render and serve

```js
import express from 'express'
import { renderToString } from '@baloise/ds-core/hydrate'

const fragment = `
  <ds-root>
    <main class="ds-container mt-base">
      <h1 class="ds-heading">Hello World</h1>
      <button class="ds-button">Button</button>
    </main>
  </ds-root>
`

async function renderPage() {
  const { html } = await renderToString(fragment, {
    // Render only the fragment, not a full <html> document — for embedding into an
    // existing CMS page template. Omit (defaults to `true`) to get a full document.
    fullDocument: false,
    // Real shadow DOM, sent as part of the HTML response (the default).
    serializeShadowRoot: 'declarative-shadow-dom',
  })

  return `<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Helvetia Design System</title>
    <link rel="stylesheet" href="/assets/base.tokens.css" />
    <link rel="stylesheet" href="/assets/design-system.css" />
  </head>
  <body>
    ${html}
    <script type="module" src="/assets/design-system/design-system.esm.js"></script>
  </body>
</html>
`
}

const app = express()

app.get('/', async (_req, res) => {
  res.type('html').send(await renderPage())
})

// The public folder staged by `pnpm copy-assets` — served as-is.
app.use('/assets', express.static('public'))

app.listen(3000)
```

Need a non-default brand, region, or language? Add the `<meta name="design-system-config">` tag
from the "Default HTML" section above into `<head>`, before the stylesheets.

`renderToString` embeds HTML comments and attributes (`clientHydrateAnnotations`, on by default)
that tell Stencil's runtime to **claim** the server-rendered elements rather than re-render them —
the same trick React and Next.js use for hydration, without requiring either.

**Requirements**:

- A Node.js-capable server or build step to call `renderToString` (or `hydrateDocument` /
  `streamToString` for a `Document` or streaming variant).
- A browser that supports [declarative shadow
  DOM](https://developer.chrome.com/docs/css-ui/declarative-shadow-dom) (Chrome/Edge, Safari 16.4+,
  Firefox 123+) — the design system's default target already assumes evergreen browsers.
- The client loader script still included, so interactive components pick up their event listeners
  after claiming.

Components that never need interactivity (e.g. a static header or footer) can be listed in
`staticComponents` — they render once and are excluded from client-side hydration entirely.

See the [`integration-ssr`](https://github.com/baloise/design-system/tree/next/apps/integration-ssr)
app in the repo for a working example.

<WarningQuote>
**Note**

This renderer (`dist-hydrate-script`, generated by Stencil) is framework-agnostic by design and is
what powers SSR for `@baloise/ds-react` under the hood. Calling it directly from a plain
Node/CMS pipeline, as shown above, is exercised by the `integration-ssr` example app linked above —
still verify the output against your specific CMS/templating stack before relying on it in
production.

</WarningQuote>

## CDN

Prototyping or don't want to install anything? Load everything straight from
[jsDelivr](https://www.jsdelivr.com/), a CDN, by adding these to `<head></head>`:

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@baloise/ds-tokens/css/base" />
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@baloise/ds-styles/css/design-system" />
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@baloise/ds-styles/css/utilities" />
<script
  type="module"
  src="https://cdn.jsdelivr.net/npm/@baloise/ds-core/dist/design-system/design-system.esm.js"
></script>
<script
  nomodule
  src="https://cdn.jsdelivr.net/npm/@baloise/ds-core/dist/design-system/design-system.js"
></script>
```

Same as before, only `base.tokens.css` and `design-system.css` are really required — drop
`utilities.css` if you don't use utility classes. The rest of the page (the
`<meta name="design-system-config">` tag, `<ds-root>`, etc.) works exactly like the "Default HTML"
section above — only where the CSS/JS come from changes.

## Client-Side (Vite)

Vite is the recommended setup for a client-side React SPA.

```bash
npm create vite@latest my-app -- --template react-ts
```

<InfoQuote>
  **Recommendations**

  - Use **TypeScript**. `@baloise/ds-react` ships its own types; no extra `@types` package or `tsconfig` flags are
    needed.
  - Use **SCSS** as stylesheet format to access breakpoint mixins and more. A pre-built CSS bundle is also available.
  - `react` and `react-dom` **18** or **19** are required as peer dependencies.
</InfoQuote>

### Installation

Install the React bindings and the global styles. All three packages are required.

```bash
npm add -E @baloise/ds-react @baloise/ds-styles @baloise/ds-tokens
// or
pnpm add -E @baloise/ds-react @baloise/ds-styles @baloise/ds-tokens
```

### Usage

Component styles are automatically loaded lazily in the browser.

Global CSS (design tokens, fonts, resets, utilities) needs to be imported into the application.

```typescript
// Required: design tokens (--ds-* CSS custom properties).
// Load before ds-styles
import '@baloise/ds-tokens/css/base'

// Required: CSS reset, structural styles, and
// CSS-only component classes (e.g. class="ds-button")
import '@baloise/ds-styles/css/design-system'

// Optional: only needed if you use utility classes
// (spacing, layout, typography, color helpers, etc. — e.g. class="mt-base" below)
import '@baloise/ds-styles/css/utilities'
```

### DsRootProvider

Wrap the application in `DsRootProvider`. It is the React root for Design System config: it initializes the system once and renders `DsRoot` so nested components pick up brand, region, language, and animation settings.

```tsx
// main.tsx

import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'

import App from './App'

// Required: design tokens (--ds-* CSS custom properties).
// Load before ds-styles
import '@baloise/ds-tokens/css/base'

// Required: CSS reset, structural styles, and
// CSS-only component classes (e.g. class="ds-button")
import '@baloise/ds-styles/css/design-system'

// Optional: only needed if you use utility classes
// (spacing, layout, typography, color helpers, etc. — e.g. class="mt-base" below)
import '@baloise/ds-styles/css/utilities'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

Pass live config as props. If you omit them, components still work with the default config. Region and language can also be changed at runtime — update the props from React state. See **Development/Internationalization**.

```tsx
// App.tsx

import { DsRootProvider, DsAppFooter, DsButton, DsHeading } from '@baloise/ds-react'

function App() {
  return (
    <DsRootProvider
      className="has-sticky-footer"
      region="CH"
      language="de"
      allowedLanguages={['de', 'fr', 'it', 'en']}
    >
      <header>
        {/* Header content */}
      </header>
      <main className="ds-container">
        {/* Your application content */}
        <DsHeading>
          Hello World!
        </DsHeading>
        <DsButton>
          Button
        </DsButton>
      </main>
      <DsAppFooter>
        {/* Footer content */}
      </DsAppFooter>
    </DsRootProvider>
  )
}

export default App
```

Do not call `initializeDesignSystem()` / `bootstrapDesignSystem()` in the React entry. `DsRootProvider` replaces that.


## Server-Side Rendering (Next.js)

Plain, non-interactive components like `DsButton` or `DsInput` render on the server — no
`'use client'` needed. Import them straight into a Server Component and Next.js renders real
markup, not an empty tag.

### Installation

Same three packages as the client-side setup, plus `next` itself.

```bash
npm add -E @baloise/ds-react @baloise/ds-styles @baloise/ds-tokens next
// or
pnpm add -E @baloise/ds-react @baloise/ds-styles @baloise/ds-tokens next
```

### Configure Next.js

Keep `@baloise/ds-core` external in the Next.js server build.

**next.config.ts**

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  serverExternalPackages: ['@baloise/ds-core'],
}

export default nextConfig
```

<InfoQuote>
  In a monorepo, you may also need to point Turbopack at the workspace root:

  ```ts
  import path from 'node:path'

  const nextConfig: NextConfig = {
    turbopack: {
      root: path.join(__dirname, '..', '..'),
    },
    serverExternalPackages: ['@baloise/ds-core'],
  }
  ```
</InfoQuote>

### Root layout

`DsRootProvider`'s client build carries a top-of-file `'use client'` pragma — wrapping the root
layout in it would force the entire tree, including every page, into a client boundary and defeat
Server Components. Use `DsRootSSRProvider` instead: it needs no client boundary of its own, boots
the runtime in the browser (custom elements + config) via an internal client leaf, and passes
`children` through untouched. Keep the root layout a Server Component:

```tsx
// app/layout.tsx

import type { Metadata } from 'next'
import { DsRootSSRProvider } from '@baloise/ds-react'

// Required: design tokens (--ds-* CSS custom properties).
// Load before ds-styles
import '@baloise/ds-tokens/css/base'

// Required: CSS reset, structural styles, and
// CSS-only component classes (e.g. class="ds-button")
import '@baloise/ds-styles/css/design-system'

// Optional: only needed if you use utility classes
// (spacing, layout, typography, color helpers, etc. — e.g. class="mt-base" below)
import '@baloise/ds-styles/css/utilities'

export const metadata: Metadata = {
  title: 'My App',
}

export default function RootLayout({ children }: Readonly<{ children: React.ReactNode }>) {
  return (
    <html lang="en">
      <body>
        <DsRootSSRProvider region="CH" language="de" animated={false}>
          {children}
        </DsRootSSRProvider>
      </body>
    </html>
  )
}
```

<InfoQuote>
`DsRootSSRProvider` does not render `<ds-root>` itself — its SSR wrapper would flatten `children`
into static HTML, breaking every interactive component nested inside it. It only boots the
runtime; add `<ds-root>` yourself as a plain tag around your layout if you need it for CSS/layout
purposes.
</InfoQuote>

### Pages

Plain, non-interactive components render straight from a Server Component page — no imports from
a `'use client'` file, no `DsRootProvider`:

```tsx
// app/page.tsx

import { DsButton, DsCheckbox, DsInput } from '@baloise/ds-react'

export default function HomePage() {
  return (
    <main>
      <h1>Hello World</h1>
      <DsButton>Click me</DsButton>
      <DsInput name="example" />
      <DsCheckbox>Accept</DsCheckbox>
    </main>
  )
}
```

<WarningQuote>
**Overlays need `window`**

Modal/Toast/Snackbar idioms are `useState`- and imperative-controller-driven — server-rendering
them has no meaning, and their generated wrappers need `window` / custom-element upgrade at
import time. Disable SSR for pages that use them with `next/dynamic`:

```tsx
'use client'

import dynamic from 'next/dynamic'

const OverlaysDemo = dynamic(() => import('./overlays-demo'), { ssr: false })

export default function OverlaysPage() {
  return <OverlaysDemo />
}
```

</WarningQuote>

### Verify server rendering

Test server rendering with a production build — `next dev` does not produce the same output, so
don't use it to verify SSR:

```bash
next build
next start
```

Open the page source and look for `shadowrootmode` inside a rendered `ds-*` element. This confirms
the server response contains Declarative Shadow DOM before JavaScript runs.

See the [integration-next](https://github.com/baloise/design-system/tree/next/apps/integration-next)
app in the repo for a working example, including the `overlays-demo` referenced above.
